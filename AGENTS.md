# Agent guide — Dark Chronicles Companion

Unofficial companion web app for Dark Chronicles (Dark Cloud 2): chapter/collectable tracking, guides, and an optimal weapon-build planner. Static site (Astro 7 SSG) with React islands, shadcn/ui (base-nova, neutral) and Tailwind v4. Everything user-specific lives in the browser (localStorage).

Read `README.md` for what the app does, `CONTRIBUTING.md` for setup, commands, checks and the game-data and built-in-plan workflows, `docs/planning.md` for how the weapon planner and the built-in plans work (and the measurements behind their rules), and `.local/plan.md` for decisions, status and the backlog (`.local/` is git-ignored: it also holds the source guides, never commit those). This file is the code map, the conventions and the pitfalls.

## Working as an agent

- Run the dev server with `astro dev --background` and manage it with `astro dev stop|status|logs`.
- Before finishing a change run the checks `CONTRIBUTING.md` lists for it, and mention in your summary anything you could not verify.

## Where things are

- `src/db/schema.ts` – the game-data database schema (Drizzle, SQLite); `drizzle/` holds its migrations and `game.db`, the committed database and the single source of truth for game data. `scripts/db/` checks it and exports it (`export.ts`) into `src/gamedata/` (generated, git-ignored; shapes in `src/lib/gamedata/types.ts`), via the `integrations/gamedata.ts` Astro integration and a Vitest global setup. The app reads it through `src/lib/gamedata/` (`index.ts`: names, chapters/sections, collectables; one module per other file; floor detail and the bestiary load on demand). `src/lib/data.ts` turns it into chapters, sections, checklist items and medals; tick ids are `<kind>:<id>` (`gamedata/ticks.ts`); `gamedata/legacy-ids.json` maps the ids from before the database (state version 2, content files version 2) and must be kept.
- `data/generated/plans/<guide id>.json` – the built-in plans (a "balanced", an "earliest" and a "gilda-max" plan for every final weapon: balanced follows the story rules; earliest follows them too but does every step as soon as it unlocks, grinding as much ABS as it takes, `earliestSteps`; gilda-max is the least-ABS path with any items as of chapter 7 and any gilda, `anyGilda`, without the story rules), committed (`{ name, spec, guide }`, `scripts/planner/plan-files.ts`), configured in `scripts/planner/plans.config.ts` under keys `<target>/<variant>` (most pin the weapon guide's build-up `route`). A guide id is the target plus a 6-hex-digit hash of its content when first generated (e.g. `island-king-42c60d`) and never changes: profiles keep ticks and dashboard switches under it. Plans are generated only on purpose (`pnpm plans`, `scripts/planner/predefined.ts`; options in `CONTRIBUTING.md`): each plan is solved `--runs` times in parallel worker processes (the solver stops at a time limit, 360 s per route for Balanced and 120 s for the slower Earliest and Gilda max, so runs differ a little), and the best run is compared with the committed plan (`plan-score.ts`: valid, then for story plans the least story cost, i.e. the solver's objective recomputed from the guide with the current settings, then earliest finish, least earning effort, least ABS, earliest pace, least gilda); the file only changes when a run is better. Plans are reviewed and committed, and are independent of the code afterwards: builds and tests never re-solve them, they only assemble the files into `src/data/plans.json` (git-ignored), which the app reads; `src/lib/guide/plans.test.ts` checks every plan is simulator-valid and reaches its goal. `src/lib/schemas.ts` – the planner's weapon/stat shapes (zod).
- `src/lib/weapons/` – pure game mechanics (ABS curve, levelling, spectrumize, build-up). Verified against the weapon FAQ's worked examples; do not "simplify" the formulas.
- `src/lib/planner/` – `simulate.ts` is the source of truth for rules; `solve.ts` builds a MILP (HiGHS wasm, `highs.ts`; row/column names must be `\w` only) per build-up chain; `plan.ts` ranks chains, solves the best few exactly (a solve that times out without a plan is retried with 4× the time), then adds the wanted abilities as +5 spheres of side weapons that carry them (coins only as a fallback, Spheda-only coins last), and finally tops up final stats a point short with items (levelling the finished weapon for SP, to at most +5). Other pieces: `sources.ts` (weapons, items, shops, `supportAllyByType`/`allyBonus`: +1 SP per level only for wrenches/hammers, swords and guns; allies with a recruit last chapter, i.e. Lin, never count), `candidates.ts` (`itemPool`: `cheap` = Conda's Goods and Antidote Drink, `crystals` = plus crystals and Knight Boots, `all`), `templates.ts` (sphere-weapon templates with the abilities they pass on; `shells` for story plans), `timeline.ts` (placing stages on the story: `placeResult`, kill sections by an enemy's earliest namesake), `worker.ts`/`client.ts` (off the main thread).
  - **Story plans** (`progression`, `STORY_RULES`, details in `docs/planning.md`; the built-in plans and the planner page's "Follow the story"): every stage gets a chapter (binary variables, any chapter from its unlock on: nothing is capped, a stage waits as long as it must) and may only use the items, spheres, ABS and gilda (plus a 30% grind allowance) available by then; no ally-dependent work before chapter 2; weapons on the way are capped at +10 (the last at +15); a weapon whose next build-up is locked to a later chapter gets in-between stages (on the same weapon) that already meet the build-up's requirements; spheres are "shells" whose items the model chooses (an exact integer bound on the 60% transfer); wanted abilities come from spheres placed where no later build-up cancels them, as early as they can (ABS Up and Wealth near-hard); the objective weighs ABS by the effort of earning it in its chapter, prefers earlier stats, charges items synthed straight onto the main weapon and keeps every stat at half the weapon's maximum when leaving it (a near-hard stat floor). These are fixed rules (`STORY_RULES` in `plan.ts`, measured in `docs/planning.md`), not settings; a plan only chooses its route, item set, least level before each build-up (`buildUpLevel`, 4 or 5, soft) and prepare steps (`prepareSpheres`). Requirements get a 1-point margin (a retry uses 3 and spare SP).
- `src/lib/guide/` – the unified guide model (`types.ts`), generated main walkthrough (`main.ts`), derived build data (`derive.ts`, never stored: stats, costs, requirements, what each sphere passes on), plans to guides (`fromPlan.ts`: a work step per weapon and chapter, a build-up step between weapons), `buildItems.ts` (a stage's or step's items, sphere contents included), `prepare.ts` (plans with `prepareSpheres`, so far Five-Star Armlet: side weapons for spheres levelled in earlier "prepare" steps, the spheres marked `prepared`), progress/dashboard helpers, legacy converters.
- `src/lib/profiles.ts` (state version 3, migrations from v2 ids and `profiles-v1.ts`; planner inputs incl. item set, solve time and "follow the story"), `src/lib/store.ts` (nanostores, persistence key `dcc:state`), `src/lib/shopping.ts` (the shopping list, derived from the game data; build goals count sphere contents).
- `src/components/` – React islands (`dashboard/`, `guide/`, `guides/`, `planner/`, `items/`, `weapons/`, `minigames/` (the Ridepod, Monster and Spheda trackers), `settings/`, `shopping/`, `tools/` (the synth sphere calculator), `db/` (the database: `kit.tsx` shared list and page parts, the list islands, and `pages/` with the pages of single things, which render on the server only), `ui/` = shadcn). `src/pages/` – Astro routes; client-only pages use `client:only="react"` and read `?id=` etc. Main sections (`components/nav.ts`): Dashboard, Guides, Tools (`/tools` hub, `/tools/planner`, `/tools/planner/editor`, `/tools/shopping`, `/tools/spheres`) and Database (`/db`).
- **The database (`/db`)**: `src/lib/db/routes.ts` has every path (`DB_LISTS`, `dbHref(kind, id)`, monster forms under their class `/db/monsters/<class>/<form>`, floors `/db/floors/<id>`, story sections link to their chapter); link with it, never by hand. List pages (`/db/<list>`) get their rows from `src/lib/db/lists.ts` at build time as island props (so they can use the whole database without shipping it); pages of single things (`/db/<kind>/<id>`, about 1,500) are static and read `src/lib/db/data.ts` (every file, the bestiary and all floor detail, plus reverse lookups), which islands must not import. Lists sort lowest first with a direction toggle: weapons by tier (`weapons.tier`, the column on Valken Lee's build-up charts, entered by hand; a build-up never goes to a lower tier), monster forms by evolution stage, the rest by chapter, Notes number or tier; shops by name. Strings are in `src/i18n/en-db.ts`. Build-up maps: `src/lib/weapons/map.ts` lays them out (tiers as columns, a layered layout), `components/weapons/BuildUpMap.tsx` draws them (the weapon list's Map view, the family map on weapon pages); weapon plans (guides and the planner's result) have Steps | Map | Detailed map views (`components/guide/PlanMaps.tsx`, from the simulator's per-stage start and end states). The service worker precaches everything but the pages of single things, which it caches when opened; Settings can save them all (`integrations/pwa.mjs`, `sw-template.js`).
- `scripts/` – database checks and export (`db/`), planner scripts, icon generation. `e2e/` – Playwright specs.

## Invariants and conventions

- **Game data goes in `drizzle/game.db`**, facts only, nothing that can be calculated (workflow in `CONTRIBUTING.md`); `scripts/db/rules.test.ts` fails if the schema and the migrations drift apart. No guide prose anywhere in the repo: walkthrough text in the app is user-authored.
- **Everything is a guide** (`Guide`/`Step`/entries `text | item | section`). Weapon builds are steps with a `build` stage (work on one weapon), `prepare` steps (side weapons made ahead of time for a later step's spheres) and `buildUp` steps (the build-up into the next weapon; without one, two `build` steps on different weapons imply it, as in older guides); stats/costs are _derived_ by the simulator when shown. Built-in guides are read-only (`kind: "builtin"`); copy with `duplicateGuide`.
- **Ticks** live in `profile.checks`: data items/medals by their own ids (shared by every guide), text entries and step ticks as `g:<guide>:<step>[:<entry>]`. Progress is always computed from _switched-on_ guides only (`profile.activeGuides`).
- **Never lose stored data.** `loadState` reports unreadable data (kept as a `dcc:state:backup-*` copy) and data from a newer version (never written over); `$storageProblem` drives the banner.
- **State is versioned.** Changing the profile shape means: bump/extend the zod schema with defaults, keep old data loading (`parseState`), add a migration test. User-supplied content (imports) must pass `content-validate.ts` before it can reach the UI.
- **Planner changes** need a simulator re-check: every plan the optimiser returns must simulate with zero errors (see `plan.test.ts`). Items: "buyable" vs "found-only" is `itemAvailability()`; the profile setting `view.buyableOnly` drives the planner. Planner changes don't touch the committed plans: regenerate them when they should change (`pnpm plans`, see `CONTRIBUTING.md`) and commit the files with the change.
- **i18n:** all UI strings go through `useTranslations()` / `src/i18n/en.ts` (the database pages' strings are in `en-db.ts`); add keys there, don't hard-code text in components. Keys are typed, so dynamic keys need `as const` casts.
- **Islands hydrate late:** server-rendered markup is clickable before React takes over. In e2e use the `go()` helper (waits for hydration). Components must not render differently on the first client render than on the server: read app state through `useAppState` / `useProfile` / `useChecks` / `useReady` (`src/lib/useAppStore.ts`), never `useStore($state)` directly; other localStorage reads need a `mounted` flag. `e2e/hydration.spec.ts` catches mismatches.
- **Navigation state lives in the URL** (`src/lib/url.ts`): tabs are paths (`/overview`, `/chapters/3`, `/tools/planner/editor`), filters and searches are query parameters (`useQueryChoice`, `useQueryText`), tracker jumps are the hash. Islands whose first render depends on the query or on saved data wrap their content in `<Gate>` so the server's defaults never flash on reload. Client-only islands read the URL in `useState` initializers, not effects. Open/closed groups and dialogs stay in component state.
- Formatting is oxfmt; it rewrites files (including generated Markdown), so run `pnpm fmt` after generating and don't rely on exact source text when scripting edits.
- Shell: quote Astro dynamic route paths (`'src/pages/db/weapons/[id].astro'`) in zsh.
- `astro preview` keeps a lock file; Playwright's config passes `--ignore-lock` and never reuses a running server so it always tests a fresh build.

## Gotchas learned the hard way

- Servers that send `Vary: Origin` break cache matching for module scripts/fonts in the service worker; `integrations/sw-template.js` matches with `ignoreVary` (covered by the offline e2e).
- The in-app/desktop browser pane cannot register service workers; use Playwright for offline checks.
- YALPS was too slow for the planner's MILP; HiGHS (wasm, ~3.4 MB) is loaded lazily and run in a worker. Its LP parser aborts ("Unable to read LP model") on names with `-` (e.g. `abs-up`).
- Story-plan solves need time: below ~10 s per route solves often end without a plan; the built-in Balanced plans use 360 s (at 120 s Island King came out 9,000 ABS worse and a chapter later), Earliest 120 s, the planner page 15–120 s (twice that for story).
- After builds or dependency changes a running `astro dev` can answer "504 Outdated Optimize Dep" and pages stop hydrating: restart the dev server.
- The site is built for the GitHub Pages base path `/dark-cloud-companion` when `PUBLIC_SITE_URL` is set; Playwright's web server sets it, so e2e URLs include the base.
- Source guides contain typos and conflicting values; the data in `game.db` was cross-checked against several guides when imported, and the disagreements are noted in `.local/import-notes.md`.
